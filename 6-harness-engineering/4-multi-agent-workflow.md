# 6.4 多 Agent 与 worktree

多 Agent 的价值在角色拆分。没有文件边界和集成责任时，多 Agent 只会把冲突放大。

## 三个基础角色

| 角色 | 职责 | 禁止 |
|---|---|---|
| Scout | 调研、找文件、列风险 | 不改代码 |
| Builder | 按计划实现 | 不扩大范围 |
| Verifier | 审查、跑验证、找问题 | 不写主体实现 |

比起让一个 Agent 从头到尾处理全部工作，这个分工更容易控制范围，也更容易把实现和审查分开。

## 什么时候适合多 Agent

适合：

- 调研和实现可以分开。
- UI 和 API 文件边界清楚。
- 两个方案可以并行探索。
- 需要独立代码审查。
- worktree 能隔离改动。

不适合：

- 文件边界不清楚。
- 任务很小。
- 多个 Agent 都要改同一个主要文件。
- 没有人做最终集成。

## worktree 的意义

worktree 让多个 Agent 在不同工作区改代码，避免互相覆盖。

适合：

```text
Agent A: 改前端页面。
Agent B: 改 API。
Agent C: 补测试。
```

不适合：

```text
三个 Agent 同时改 auth 主要模块。
```

## 多 Agent 前置清单

- 每个 Agent 的目标是否清楚？
- 每个 Agent 的文件范围是否清楚？
- 是否有共享文件？
- 谁负责集成？
- 用什么测试证明集成成功？
- 失败时怎么回滚？

如果清单无法回答，不要并行实现。
